# AGENTS.md

Rules for AI coding agents working in this repository. People should read
[CONTRIBUTING.md](CONTRIBUTING.md); everything here applies to them too. The
`PR rules` check enforces the rules marked (checked); a pull request that
breaks one cannot be merged.

## What lumenparty is

A Claude Code plugin: subagents (`agents/`), skills (`skills/`), guard hooks
written in bash (the spells in `wol/spells/`, wired up by `hooks/hooks.json`),
a merge gate (`wol/crystal/gate.sh`) and the `lumenparty` command (`bin/`).
`install.sh` installs the same into a project without the plugin system.

Read before you touch:

- a spell: the "Ground rules" in CONTRIBUTING.md, the README sections "The
  spells (hooks, zero tokens)" and "What Protect can and cannot see",
  `wol/lib.sh` and `tests/cases.txt`.
- a hero or skill: `agents/*.md` and `skills/*/SKILL.md` are generated by
  `tools/gen_agents.py` and `tools/gen_skills.py`. Edit those, never the
  generated files.
- the gate: the README section "The Crystal Gate" and `wol/crystal/gate.sh`.
- the benchmark: `bench/README.md`.

## Commands

Every one of these must pass before you open or update a pull request. CI
(`.github/workflows/ci.yml`) runs the same ones, with Dart installed so the
benchmark checks in `tests/run.sh` run too:

```bash
shellcheck -S warning install.sh uninstall.sh tests/run.sh bin/lumenparty bin/wol wol/lib.sh wol/spells/*.sh wol/crystal/*.sh bench/run.sh bench/tasks/*/check.sh
python3 tools/gen_agents.py && python3 tools/gen_skills.py
git diff --exit-code -- agents skills
tests/run.sh
bench/run.sh --dry
```

Check one Protect decision while iterating:
`jq -n --arg c 'git push origin main' '{tool_input:{command:$c}}' | wol/spells/protect.sh`

## Stop and ask the human

Some things must come from the real world. An agent must never invent them.
Stop and ask the person you work for to provide them:

- **Claude Code behaviour.** Hook input and output fields, `onFailure`,
  matchers, the plugin layout and the minimum Claude Code version come from
  the Claude Code documentation or changelog. Cite it; never guess a field
  name or a version.
- **Real command lines.** A rule about git, gh, a store, release or deploy
  tool, or SQL matches commands that really exist: take the syntax from the
  tool's documentation or a real run, with the version. A bypass report is a
  real command line, run against `wol/spells/protect.sh`.
- **Benchmark results.** Scores and costs come from a real `bench/run.sh` run
  by the human; it spends money. Never run it without `--dry`, and never
  write or change a result.
- **An accepted issue.** If the change has no issue labelled `accepted`, stop
  and ask the human to open one and wait for a maintainer.

## Code

- **English only** for code, identifiers, comments, commit messages and docs.
  Translations go only where the repository already keeps them, such as
  `README.id.md`. Answer the person you work for in their language.
- Shell targets bash 3.2 (macOS) and Linux. The spells need nothing beyond
  `jq`, `git` and `perl` (`gh` for the gate).
- Patterns go in `wol/config.sh` or a preset in `wol/presets/`, not hardcoded
  in a spell. Every guard fails closed.
- Least code that works (`skills/auron/SKILL.md`). Comments are sparse: only
  where the code is not self-evident. Do not add comments to code you did not
  change.

## Tests (checked)

- Every change to `bin/`, `hooks/`, the `.sh` and `.json` files in `wol/`,
  `install.sh`, `uninstall.sh` or a `bench/tasks/*/check.sh` comes with a test
  change under `tests/`: a line in `tests/cases.txt` (`expected|tool|input`)
  for a spell decision, a check in `tests/run.sh` for the rest. It fails
  without the change; check that it does before you open the pull request.
- A benchmark check is tested both ways in `tests/run.sh`: it rejects the
  untouched fixture and accepts a correct solution.

## Never

- Never silence shellcheck (checked): no new `# shellcheck disable` lines in
  the shell files, no `.shellcheckrc`. Fix the finding instead.
- Never delete, skip, loosen or rewrite an existing test or `tests/cases.txt`
  line to make CI pass. If a test looks wrong, say so in the issue.
- Never weaken a guard: a command a spell denies stays denied, and every
  PreToolUse hook keeps `"onFailure": "block"`, unless the issue asks for
  exactly that.
- Never rename a hero, skill, `lumenparty` subcommand or `WOL_*` config key.
  Users' configs, prompts and hooks name them.
- Never edit `agents/` or `skills/` by hand.
- Never change the version in `.claude-plugin/plugin.json`, edit a released
  `CHANGELOG.md` section, tag or release. Add your entry at the top of
  `CHANGELOG.md` under `## Unreleased` (create the heading if it is missing).
- Never add a dependency or change CI workflows unless the issue asks for it.
- Never hardcode a company, app or person name in code, presets or prompts:
  lumenparty is project-agnostic.
- Never add unrelated "improvements": no drive-by refactors, renames,
  reformatting of untouched code or dead code.
- Never open pull requests, issues or comments on your own. The human reviews
  your work and posts it.

## Pull requests (checked)

- First an issue, labelled `accepted` by a maintainer. The pull request says
  `Closes #N`.
- One issue per pull request, at most 400 changed lines.
- At most 2 open pull requests per person.
- Fill in the pull request template, including `### AI use` with the tool and
  model.
- The person submitting has read, run and understood every line, and writes
  the description in their own words. Pull requests that are raw, unreviewed
  agent output will be closed.
